# Rust Async / Await

Rust's async model lets you write **concurrent** code that looks like
sequential code. It is the standard way to handle many simultaneous I/O
operations (web servers, network clients, scrapers) without spawning an OS
thread per task.

## The Core Idea

`async fn` returns a **Future** — a state machine generated by the
compiler. The function body **does not run** until something **polls** the
future. `.await` is the operator that polls a future from inside another
async fn.

```rust
async fn hello() -> String {
    String::from("hello!")
}

// `hello()` returns a Future<Output = String> — it has not run yet.
// We must `.await` (or hand to a runtime) to actually execute it.
let s = hello().await;
```

## Three Key Facts

1. **Async functions are lazy.** Calling `hello()` does nothing — it just
   builds a state machine.
2. **Futures do nothing without an executor.** You need a runtime
   (`tokio`, `async-std`, `smol`) to poll them.
3. **`.await` only works inside `async fn`.** It is the bridge between
   async functions.

## `async fn` vs Regular `fn`

```rust
// Regular function — runs to completion when called.
fn add(a: i32, b: i32) -> i32 { a + b }

// Async function — returns a Future that, when polled, computes a + b.
async fn add_async(a: i32, b: i32) -> i32 { a + b }
```

`async fn foo(args) -> T` is sugar for:

```rust
fn foo(args) -> impl Future<Output = T>
```

## `.await` in Action

```rust
async fn greet(name: &str) -> String {
    let part1 = hello().await;          // pauses greet until hello is done
    let part2 = format!(", {}", name);
    format!("{}{}", part1, part2)
}
```

When `hello().await` returns `Pending`, `greet` yields control back to the
executor, which can run other tasks. When `hello` is ready, `greet`
resumes.

## Why Async? Concurrency Without Threads

A web server handling 10,000 simultaneous connections:

* With **threads**: 10,000 OS threads — each ~2 MB stack = 20 GB of memory.
* With **async**: 10,000 tasks on a thread pool — a few MB total.

Async tasks are **state machines** stored on the heap. They are tiny
compared to OS threads.

## Concurrency vs Parallelism

| | Concurrency | Parallelism |
|---|--------------|-------------|
| Many tasks in flight | yes | yes |
| Running at the same instant | not necessarily | yes |
| Single-core | possible | impossible |
| Async gives | concurrency | (with multi-thread runtime) also parallelism |

A single-threaded async runtime gives **concurrency** (tasks interleave on
one thread). A multi-threaded runtime like tokio also gives **parallelism**.

## A Real Example with Tokio

Add to `Cargo.toml`:

```toml
[dependencies]
tokio = { version = "1", features = ["full"] }
```

Then in `src/main.rs`:

```rust
#[tokio::main]
async fn main() {
    let body = fetch_url("https://example.com").await;
    println!("{}", body);
}

async fn fetch_url(url: &str) -> String {
    // (Pseudo-code — you'd use reqwest or hyper here)
    url.to_string()
}
```

`#[tokio::main]` is a macro that wraps your async `main` in a runtime:

```rust
fn main() {
    tokio::runtime::Runtime::new().unwrap().block_on(async_main())
}
```

## Spawning Tasks

`tokio::spawn` runs a future on the runtime in the background:

```rust
#[tokio::main]
async fn main() {
    let handle = tokio::spawn(async {
        // Some background work
        42
    });

    let result = handle.await.unwrap();
    println!("{}", result);
}
```

## Channels Between Tasks

```rust
use tokio::sync::mpsc;

#[tokio::main]
async fn main() {
    let (tx, mut rx) = mpsc::channel(32);

    tokio::spawn(async move {
        for i in 0..10 {
            tx.send(i).await.unwrap();
        }
    });

    while let Some(msg) = rx.recv().await {
        println!("got {}", msg);
    }
}
```

## Selecting Between Futures

```rust
use tokio::select;

async fn race() {
    select! {
        a = async_task_a() => println!("a won: {}", a),
        b = async_task_b() => println!("b won: {}", b),
    }
}
```

The first future to complete wins; the others are dropped.

## Async Cancellation

Dropping a future **cancels** it. There is no special "cancel" method —
the future's destructor runs when it is dropped:

```rust
let task = tokio::spawn(async { /* ... */ });
// To cancel:
task.abort();
```

## Pinning — Why Futures Need `Pin`

Many futures are **self-referential** (they hold references to their own
state). Moving such a future would invalidate those references. `Pin<P>`
is a pointer wrapper that promises the value will not be moved.

You usually don't write `Pin` yourself — `.await` and `Box::pin` handle
it. But you'll see it in signatures:

```rust
fn poll(self: Pin<&mut Self>, cx: &mut Context<'_>) -> Poll<Self::Output>;
```

## `Send` Futures

To move a future between threads (e.g. to send to a multi-thread runtime),
it must be `Send`. The compiler enforces this — if your future holds a
non-`Send` type (like `Rc`), it will not be `Send`.

```rust
tokio::spawn(async {
    let rc = std::rc::Rc::new(5);   // ERROR: Rc is not Send
    // ...
});
```

Use `Arc` instead, or run the task on a single-threaded runtime.

## Pitfalls — What NOT to Do

### Don't Block Inside Async

```rust
async fn bad() {
    std::thread::sleep(Duration::from_secs(1));   // BLOCKS THE WORKER THREAD
}
```

Use the runtime's sleep instead:

```rust
async fn good() {
    tokio::time::sleep(Duration::from_secs(1)).await;   // yields to runtime
}
```

### Don't Use `std::sync::Mutex` for Long Holds

`std::sync::Mutex` blocks the OS thread while waiting. Inside async code,
this stalls the runtime. Use `tokio::sync::Mutex` if the lock is held
across `.await`:

```rust
use tokio::sync::Mutex;
use std::sync::Arc;

let data = Arc::new(Mutex::new(0));
let d = Arc::clone(&data);
tokio::spawn(async move {
    let mut guard = d.lock().await;
    *guard += 1;
});
```

For short-lived locks not held across `.await`, `std::sync::Mutex` is fine
and faster.

### Don't Forget to Await

```rust
async fn work() { /* ... */ }

fn caller() {
    work();   // BUG: returns a Future, never runs it — silently does nothing
}
```

Always either `.await`, `tokio::spawn`, or `block_on` the future.

## When to Use Async

| Use async | Use threads |
|-----------|-------------|
| Many I/O-bound tasks (1000s of connections) | CPU-bound work |
| Web servers, scrapers, chat apps | Small concurrent scripts |
| Need to scale to thousands of tasks | Pin-point parallelism |

## Async Ecosystem

| Crate | Purpose |
|-------|---------|
| `tokio` | The dominant async runtime (multi-threaded) |
| `async-std` | Alternative runtime mirroring std's API |
| `smol` | Small, simple runtime |
| `futures` | Future / Stream combinators |
| `reqwest` | Async HTTP client |
| `hyper` | Async HTTP server/client (low-level) |
| `axum`, `actix-web` | Async web frameworks |
| `sqlx` | Async database driver |

## A Mental Model

* An **async fn** is a recipe that hasn't been cooked yet.
* A **Future** is the recipe plus a "where was I?" bookmark.
* **Polling** is asking the recipe "are you done yet?" — it might run a
  little more and then say "not yet, ask again later."
* The **executor** is the chef that asks all the recipes "done yet?" in a
  loop.
* **`.await` is asking one recipe "are you done?" inside another recipe** —
  if not, both yield back to the chef.

## Cheat Sheet

```rust
async fn fetch(url: &str) -> String { /* ... */ String::new() }   // returns Future

let s = fetch("...").await;          // poll the future to completion

tokio::spawn(async { /* ... */ });   // run a future in the background

// Cargo.toml:
// tokio = { version = "1", features = ["full"] }

// main:
#[tokio::main]
async fn main() { /* ... */ }
```
